# Архитектура системы «Охрана труда»

## 1. Общая схема

```
Браузер (React SPA) ──HTTPS──▶ Caddy (TLS, опц.) ──▶ nginx (статика, CSP, /api proxy) ──▶ NestJS API ──▶ PostgreSQL
                                                                                              │
                                                              файлы вложений (том uploads) ◀──┤
                                                              резервные копии (том backups) ◀─┘◀── сервис backup (pg_dump)
```

* **Модульный монолит.** Каждый раздел — отдельный NestJS-модуль (`backend/src/<модуль>`); новые разделы
  добавляются новым модулем без изменения существующих.
* **Бизнес-логика вынесена в чистые функции** (`*.logic.ts`, `compliance/rules.ts`) — покрыта unit-тестами
  и не зависит от БД.
* **Проверка прав только на сервере**: глобальные guard'ы `JwtAuthGuard` + `PermissionsGuard`,
  ограничение по подразделениям — в каждом запросе (`common/scope.ts`). Интерфейс лишь скрывает недоступные действия.
* **Журналирование**: глобальный `AuditInterceptor` пишет все изменяющие запросы в `audit_logs` (секреты маскируются).
* **Фоновые задания**: `@nestjs/schedule`, ежечасно; защищены advisory-lock PostgreSQL от параллельного запуска
  на нескольких экземплярах, идемпотентны (уникальные ключи уведомлений и задач).

## 3. Ролевая модель

Разрешения (`backend/src/common/permissions.ts`) хранятся в БД; набор разрешений роли меняется администратором
(раздел «Роли и права»). Стартовые роли: системный администратор, специалист по ОТ, руководитель подразделения,
кадровый специалист, ответственный за выдачу СИЗ, аудитор. Зона доступа пользователя — «все подразделения»
или перечень подразделений (с дочерними). Руководителю можно точечно выдать, например, `briefings.conduct`.

## 4. Схема БД (PostgreSQL, Prisma, миграции в `backend/prisma/migrations`)

Требуемые сущности и их таблицы: `users`, `roles`, `permissions`, `role_permissions`, `user_roles`,
`user_unit_scopes`, `refresh_tokens`, `organizational_units`, `positions`, `employees`, `employee_history`,
`briefing_types`, `briefing_rules`, `briefings`, `briefing_participants`, `knowledge_check_types`,
`knowledge_check_rules`, `commissions`, `commission_members`, `knowledge_checks`, `knowledge_check_participants`,
`knowledge_check_results`, `safety_documents`, `ppe_items`, `ppe_standards`, `ppe_issues`, `ppe_returns`,
`ppe_stock_movements`, `tasks`, `notification_rules`, `notifications`, `notification_deliveries`, `attachments`,
`document_templates`, `audit_logs`, `system_settings`, `import_jobs`, `import_errors`.

Принципы:
* календарные даты — `DATE`, моменты времени — `TIMESTAMPTZ`; «сегодня» — в часовом поясе `APP_TIMEZONE`;
* записи контрольного значения не удаляются: `onDelete: Restrict`, статусы (`CANCELLED`, `ARCHIVED`, `isActive`),
  увольнение не затрагивает историю; файлы архивируются;
* участники мероприятий и выдачи СИЗ хранят **подразделение и должность на момент события** — исторические
  отчёты корректны после переводов;
* уникальность: табельный номер, `(briefingId, employeeId)`, `(userId, dedupeKey)` уведомлений, `sourceKey` автозадач;
* автор и время изменения — `createdById/updatedById`, `employee_history.authorId`, `audit_logs`.

## 5. Ключевая бизнес-логика

**Правила периодичности** (`compliance/rules.ts`). Правило: вид мероприятия + (должность | категория работ |
подразделение | общее) + период (мес./дн.) + срок первичного прохождения + признак «повторно после перевода»
+ основание + период действия. Выбирается наиболее специфичное правило, действовавшее **на дату мероприятия**;
рассчитанная дата следующего прохождения сохраняется вместе с правилом — изменение правил не переписывает историю.

Состояния: `OK`, `UPCOMING`, `OVERDUE`, `MISSING` (нет прохождения после приёма/перевода), `FAILED`
(неудовлетворительный результат после последнего успешного). Инструктаж засчитывается только с результатом
«прошёл» и — если вид требует — с зафиксированным подтверждением. Проверка засчитывается только при
результате «удовлетворительно».

**СИЗ** (`ppe/ppe.logic.ts`). Потребность = действующие нормы должности − числящееся (за вычетом возвратов/списаний)
+ единицы с просроченной плановой заменой. Запись о выдаче без подтверждения получения даёт статус
«Ожидает подтверждения», а не «Обеспечен». Плановая дата замены рассчитывается только при календарном сроке
носки; иначе (износ, сезонность) — пусто или ручная корректировка с основанием.

**Уведомления** (`notifications`). Этапы: ближайший порог «за N дней», «в день срока», «просрочено».
Ключ идемпотентности учитывает этап и дату; повторный запуск задания не создаёт дубликатов. Доставка
фиксируется по каналам (`IN_APP`, `EMAIL` — заготовка с явным статусом `SKIPPED`).

## 6. Основные пользовательские сценарии

1. Кадровый специалист загружает Excel → предпросмотр с ошибками по строкам → загрузка корректных строк одной транзакцией.
2. Специалист ОТ открывает «Требуется инструктаж», выбирает сотрудников → планирует → регистрирует проведение
   (обязательные поля проверяются) → фиксирует подтверждение (подпись в журнале/скан) → печатает журнал.
3. Проверка знаний: план → результаты с протоколом → дата следующей проверки по правилу → печать протокола.
4. СИЗ: потребность → выдача (размер, срок носки) → подтверждение получения → возврат/списание/замена → личная карточка.
5. Руководитель видит панель и отчёты только по своему подразделению; аудитор — только просмотр.

## 7. Критерии приёмки

| Критерий | Проверка |
|---|---|
| Вход, роли, ограничения по подразделениям, блокировка, ротация refresh | e2e `Авторизация`, `ограничение по подразделениям` |
| Импорт сотрудников с предпросмотром, ошибками, без дубликатов | e2e `Сотрудники и импорт`; unit `import.logic.spec.ts` |
| Планирование и регистрация инструктажей, запрет без обязательных полей | e2e `Инструктажи`; unit `briefing.logic.spec.ts` |
| Проверки знаний, выделение неудовлетворительных результатов | e2e `Проверки знаний` |
| Учёт СИЗ, подтверждение получения, возврат, остатки | e2e `СИЗ`; unit `ppe.logic.spec.ts` |
| Сохранность истории уволенных | e2e `Увольнение и сохранность истории` |
| Уведомления без дубликатов | e2e `повторный запуск фонового задания` |
| Все 12 отчётов формируются; экспорт XLSX/PDF/CSV | e2e `все отчёты формируются` |
| Журнал действий без паролей | e2e `журнал действий` |
| Производительность на 2000 сотрудников | `seed:dev` — 2000 сотрудников; панель ≈ 1 с |
